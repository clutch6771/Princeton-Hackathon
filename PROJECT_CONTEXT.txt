5. CODING CONVENTIONS (code you write must follow these)
--------------------------------------------------------
General:
  - Immutability: return new objects; don't mutate inputs in place.
  - Small functions (<50 lines), focused files (200-400 lines, max ~800).
  - No nesting deeper than 4 levels; prefer early returns.
  - No magic numbers; use named constants.
  - Handle errors explicitly; never swallow exceptions silently.
  - Validate all external input (user input, API responses, files).
  - KISS / DRY / YAGNI.

Python:
  - Type hints on all function signatures; must pass mypy.
  - Formatted with black + isort; must pass ruff (E, F, I, B, UP, S).
  - Use the logging module, never print().
  - Secrets come from environment variables / .env via python-dotenv.
    NEVER hardcode API keys.
  - Keep agent components modular and testable.
  - Notebooks are for exploration; reusable logic goes in .py modules with tests.

Machine learning:
  - Document model inputs and outputs (shapes, types, ranges).
  - Validate data going in and out.
  - Seed every source of randomness (random, NumPy, torch, ...).
  - Never commit datasets, weights or checkpoints (.pt, .pth, .ckpt, .h5,
    .onnx, .safetensors, .pkl, data/, models/, ... are git-ignored).

Swift / iOS:
  - SwiftUI; keep UI separate from business logic.
  - Respect Swift concurrency and actor isolation (Swift 6 strict concurrency).
  - Use os.Logger, never print().
  - Protocol-based dependency injection so logic can be unit tested.
  - No secrets in source, Info.plist, .xcconfig or .entitlements.

Testing:
  - Test-driven development: write the failing test first, then implement.
  - Target 80%+ coverage. Unit + integration tests.
  - Arrange-Act-Assert structure, descriptive test names
    (e.g. test_returns_empty_list_when_no_reels_match).
  - Python: pytest (+ pytest-cov). Swift: XCTest / Swift Testing.

Git:
  - Work on a feature branch; merge to main through a pull request.
  - Commit format: "<type>: <description>"
    types: feat, fix, refactor, docs, test, chore, perf, ci
  - Never commit secrets, .env, or private data.


6. HOW TO PROMPT FOR EACH PART
------------------------------
Always state which part you're working on and paste the relevant existing
code (ChatGPT can't see the repo). Fill in the <...> parts.

A) Python agent code (watcher_Agent/)
   "Using the project context above, write a Python module for
    watcher_Agent/<name>.py that <does X>. Inputs: <...>. Outputs: <...>.
    Follow the conventions: type hints, logging not print, no mutation,
    functions under 50 lines, secrets from env vars. Also write
    pytest tests in tests/test_<name>.py first."

B) Machine learning / model work
   "I'm adding an ML component to the Reel Watcher Agent that <goal>.
    Data: <format, size, where it comes from>. Suggest a model and write
    the training/inference code with documented input/output shapes,
    input validation, seeded randomness, and tests on a tiny fixed
    sample. Don't store data or weights in the repo."

C) iOS app (Swift / SwiftUI)
   "Write a SwiftUI view/view model for <screen> in the iOS app. Swift 6,
    strict concurrency, view model as @MainActor @Observable, business
    logic behind a protocol for testing, os.Logger for logging. Include
    XCTest/Swift Testing unit tests for the view model."

D) Python <-> iOS integration (not decided yet)
   "Compare options for connecting the Python agent to the iOS app
    (e.g. FastAPI REST service, on-device Core ML conversion, a cloud
    function). Consider hackathon time limits, latency and complexity.
    Recommend one and show the API contract (request/response JSON)."
   If you pick an API: use a consistent response envelope
   {"success": bool, "data": ..., "error": str | null}.

E) Tests / debugging
   "Here is <code> and the failing output <error/log>. Find the root
    cause and fix the implementation (not the test, unless the test is
    wrong). Keep the fix minimal."

F) Code review
   "Review this code against the project conventions above: correctness,
    security (secrets, input validation), type hints, error handling,
    immutability, function size, test coverage. Rank issues as
    CRITICAL / HIGH / MEDIUM / LOW."

G) Commits and pull requests
   "Write a conventional commit message (feat/fix/refactor/docs/test/
    chore/perf/ci) for this diff: <diff>."
   "Write a PR description with a summary and a test plan checklist
    for these commits: <git log / diff>."

Tips:
  - Ask for code that passes black, ruff and mypy. The team's hook enforces
    them anyway.
  - Ask for tests together with the code.
  - If something about the architecture isn't decided, have ChatGPT ask
    rather than guess.
